Forecasting without the AI theater.

Operational teams already have metrics, dashboards and alerts. Precog adds a different capability: test whether the behavior you care about is actually forecastable, measure the evidence, and only then produce a forecast worth using.

01

Start from the operational question

Capacity, growth, utilization, workload drift. Precog is a forecasting engine, not a data-source adapter or an all-purpose observability product.

02

Backtest before trust

Evaluate held-out history, inspect per-target error and interval coverage, and compare with simple baselines before deciding whether the model adds useful signal.

03

Keep the limits explicit

Stable levels and trends may be forecastable. Sudden deployments, failures and external decisions may not be. A useful answer can be “do not forecast this”.

Designed for adoption

Agent-friendly semantics

MCP exposes forecasting and backtesting as focused semantic capabilities, not infrastructure-specific workflows.

Joint forecasting when the problem is joint

Related targets can be evaluated together even when units or numeric scales differ.

Caller-owned data preparation

Precog does not silently interpolate, truncate or mutate caller data. The meaning of the series stays explicit.

A simple discipline.

Precog deliberately keeps the workflow small: obtain the right series, define what “useful” means, backtest the forecasting problem, compare evidence, then forecast only when the result deserves it.

Step 01

Bring the series

Acquire and prepare numeric, aligned, equally sampled observations that represent the problem you actually want to forecast.

Step 02

Declare the objective

Choose a horizon that matches the operational decision instead of optimizing an abstract metric.

Step 03

Backtest the hypothesis

Use held-out evidence, simple baselines and multiple historical cutoffs when the decision matters.

Step 04

Forecast where useful

Adopt the capability where it improves the decision. Keep uncertainty and failure modes visible.

Run the real thing.

Start the full Precog capability with the published containers: the real TimesFM-3 execution API plus the MCP semantic interface. The API downloads the pinned model weights on first start and keeps them in a local cache volume for subsequent runs.

Full capability — API + TimesFM-3 + MCP
# one-time local network and persistent model cache
docker network create precog
docker volume create precog-models

# real TimesFM-3 execution API — weights download automatically on first start
docker run -d --name precog-api --network precog \
  -p 127.0.0.1:8000:8000 \
  -e PRECOG_ENGINE=timesfm3 \
  -v precog-models:/opt/precog/hf \
  ghcr.io/albe83/precog-api:latest

# agent-facing MCP server
docker run -d --name precog-mcp --network precog \
  -p 127.0.0.1:8765:8765 \
  -e PRECOG_API_URL=http://precog-api:8000 \
  -e PRECOG_MCP_TRANSPORT=http \
  ghcr.io/albe83/precog-mcp:latest

# API readiness and MCP endpoint
curl http://127.0.0.1:8000/readyz
# MCP: http://127.0.0.1:8765/mcp

The first API start downloads the TimesFM-3 weights into precog-models; later starts reuse the cache. For reproducible or production deployments, pin a released version or immutable image digest instead of latest.
